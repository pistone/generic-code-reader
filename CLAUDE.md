# Domain AI Knowledge Base — Hackathon Project

## Project Goal

Build a domain-aware AI knowledge base that lets Claude Code answer questions
about a target codebase semantically, reduces token usage for the whole team
by caching discovered knowledge, and improves itself through use via a
suggestion/reviewer agent loop.

This is a hackathon project at Blackduck/Synopsys. The key differentiator over
off-the-shelf tools (Sourcegraph Cody, claude-context, etc.) is that our index
is built from **domain-specific LLM-generated summaries** tuned for the target
domain's concepts — not raw code chunks. The summarization prompts are
themselves generated by studying the codebase structure and consulting internal
design documentation.

The system is generic: given any codebase and a set of domain knowledge docs,
it produces a knowledge base tailored to that domain's vocabulary and patterns.

## Key Design Decisions

### 1. LLM-generated summaries, not raw chunks

Raw code chunks embed poorly — the semantic meaning of domain-specific code is
implicit in the logic, not the surface text. An LLM-generated summary like
"this function checks whether a pointer dereference is safe by verifying the
pointer is non-null, used in the interprocedural null dereference checker"
embeds much better and retrieves correctly for natural language queries.

**Hybrid storage**: index the summary (for search quality), but store and return
the raw source code alongside it (so Claude reasons on ground truth, not the
summary).

### 2. Two-step study phase

**Step 1 — Module discovery**: The agent reads the directory tree and a sample
of files from each directory. `search_docs` is used in two distinct ways here:

1. **Architecture understanding** (before any questions are written): the agent
   searches design docs to understand how the system fits together — what the
   major subsystems are, how they relate, and what domain concepts like
   "checker", "IR", or "lattice" mean in this codebase. Without this step the
   agent cannot meaningfully interpret a directory name like `src/checkers/`.

2. **Concept grounding per module**: once a module is identified, the agent
   searches docs again to understand what that specific component does before
   writing its question list. "What does a checker do?" must be answered by the
   docs before the agent can ask good questions about checker files.

Only after both of the above does the agent produce the structured module map:

```json
{
  "src/checkers/": {
    "description": "Individual bug detectors",
    "questions": [
      "What bug class does this checker target?",
      "What IR patterns trigger it?",
      "What are known false positive sources?",
      "What interprocedural behavior does it have?"
    ]
  },
  "src/dataflow/": {
    "description": "Dataflow analysis engine",
    "questions": [
      "What lattice does this implement?",
      "What are the transfer function semantics?",
      "What is the meet operator behavior?"
    ]
  }
}
```

The questions are domain-specific — they reflect the vocabulary and concepts
the agent learned from the docs, not just generic code-reading questions.

**Step 2 — Summarization**: For each file, the agent uses the module's question
list as a structured prompt to generate the summary. It searches design docs
on demand when it encounters unfamiliar patterns — it does NOT load all docs
upfront.

### 3. Design docs are searchable, not preloaded

Index design documents and any reference manuals into the knowledge base
FIRST (before code indexing). The study agent has `search_docs(query)` available
as a tool and pulls relevant sections on demand. This avoids burning context
window on docs that may not be relevant to the current chunk.

**Initialization order**:
1. Index design docs + reference manual → knowledge base
2. Run study agent (has search_docs available)
3. Agent pulls doc context on demand
4. Indexer writes code summaries to knowledge base

### 4. R2R as the backend

R2R (SciPhi) is used as the vector DB + retrieval server. It runs as a Docker
container exposing a REST API on port 7272. We use the Python client library.

```python
from r2r import R2RClient
client = R2RClient("http://localhost:7272")

# Index a summary
client.documents.create(
    raw_text="summary text here",
    metadata={"source_file": "src/checkers/null_deref.cpp",
              "module": "checkers",
              "chunk_type": "function_summary"}
)

# Search
results = client.retrieval.search(query="null pointer template handling")
```

R2R uses `litellm` as its embedding provider, which supports 100+ model
providers (OpenAI, Voyage AI, Cohere, internal servers, etc.) via a unified
interface. In r2r.toml:

```toml
[embedding]
provider = "litellm"
base_model = "voyage/voyage-code-2"   # or "openai/text-embedding-3-small"
base_dimension = 1536
batch_size = 128

[completion]
provider = "litellm"
base_model = "openai/gpt-4o-mini"

[database]
provider = "postgres"
```

The API key is passed via environment variable (`VOYAGE_API_KEY`, `OPENAI_API_KEY`,
etc.) — litellm picks it up automatically. Never hardcode keys in r2r.toml.

Note: R2R's completion config is only used if you call `client.retrieval.rag()`.
For our use case (MCP server calls `search()` and hands chunks to Claude Code),
the completion config is unused. Only the embedding config matters.

### 5. MCP server design

Local Python process (~100 lines). Exposes two tools to Claude Code:

```python
@mcp_tool
async def search_codebase(query: str) -> str:
    """Search the domain knowledge base semantically."""
    results = r2r_client.retrieval.search(query=query, limit=5)
    # Log: query, tokens returned, timestamp (for experiment measurement)
    return format_results(results)

@mcp_tool
async def suggest_index_item(
    topic: str,
    summary: str,
    source_files: list[str],
    reasoning: str
) -> str:
    """Suggest a new entry for the knowledge base."""
    staging_queue.add({
        "topic": topic,
        "summary": summary,
        "source_files": source_files,
        "reasoning": reasoning,
        "status": "pending",
        "timestamp": now()
    })
    trigger_reviewer_agent()
    return "Suggestion queued for review."
```

Register with Claude Code via `.mcp.json` in project root:

```json
{
  "mcpServers": {
    "domain-kb": {
      "command": "python",
      "args": ["mcp_server.py"],
      "cwd": "/path/to/kb"
    }
  }
}
```

### 6. Reviewer agent

Triggered asynchronously when a suggestion arrives in the staging queue.
Makes its own Claude API call with these tools: `read_file`, `search_codebase`.

System prompt key points:
- Verify summary accuracy by reading cited source files
- Check for duplicates via semantic search
- Verify that descriptions use correct domain terminology and concepts
- Return JSON: `{decision: approve|edit|reject, final_summary, reasoning}`

On approve or edit: calls `r2r_client.documents.create()` with final summary.
On reject: logs to rejected_queue with reasoning for human review.

### 7. Suggestion flow (the self-improving loop)

```
Claude Code queries search_codebase()
    → Good results: return to user, done
    → Poor results: Claude researches manually (reads files, greps)
        → Claude finds answer
        → Claude calls suggest_index_item()
        → Reviewer agent wakes up, verifies, approves
        → Next developer gets instant answer from KB
        → Token cost: amortized across all future queries
```

This is the core hackathon narrative: the KB gets denser in exactly the areas
the team actually works on, weighted by real usage patterns.

## Build Order

Build in this sequence — each step is independently demonstrable:

1. **Indexer script** — takes a directory of text summaries, calls R2R to store
   them with embeddings. Verify with a manual search query.

2. **MCP server (search only)** — `search_codebase` tool only, no suggestion
   yet. Verify Claude Code can find things semantically.

3. **Study agent** — two-pass codebase analysis feeding the indexer. This is
   the main build effort.

4. **Suggestion + reviewer** — add `suggest_index_item` to MCP server, write
   reviewer agent. Demonstrate the self-improvement loop.

## Experiment / Demo Design

**Research questions to use** (pick ones that require codebase knowledge):
- "How does the null dereference checker handle pointer arithmetic across
  function calls?"
- "What is the entry point for adding a new checker?"
- "How does the dataflow engine propagate taint across call boundaries?"

**Measurement**: Log per query in the MCP server:
- Tokens in the returned chunks (proxy for context cost)
- Number of file reads Claude did without KB vs. with KB

**Without KB baseline**: Watch Claude Code's tool calls, count `read_file`
invocations, multiply by average file size in tokens (~800 tokens/file typical).

**With KB**: MCP server logs tokens returned per search call.

**Presentation slide**: One hero screenshot (wrong answer vs. right answer),
one table (5 questions × correctness + token reduction), one number (e.g. "73%
token reduction on average").

**Live demo**: Ask question live without KB (show Claude struggling), enable
MCP server, ask same question. The contrast in real time is more convincing
than any slide.

## Notes / Constraints

- **Code stays on-premise**: all model calls go to internal company servers,
  never to OpenAI or Anthropic directly. R2R is configured with internal
  base_url for both embedding and completion.
- **Git hook for freshness**: indexer re-runs on post-commit, only re-indexing
  changed files (incremental update).
- **Chunking strategy**: use tree-sitter to split at function/class boundaries
  before feeding to summarization agent. Feed individual chunks, not whole
  files, to stay within context limits.
- **Staging queue is just a JSON file** for the hackathon — no need for a real
  queue system.
- **R2R Ollama integration has known issues** (404 errors in some versions).
  Use the `provider = "openai"` config pointing at internal server instead —
  more reliable code path.
